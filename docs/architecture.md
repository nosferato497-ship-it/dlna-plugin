# Архитектура и технические ограничения

## Требуемые роли

Проект должен поддерживать два независимых сценария:

1. **MediaRenderer:** Lampa передаёт URL потока на DLNA Renderer, затем управляет транспортом через UPnP AVTransport.
2. **MediaServer:** Lampa просматривает ContentDirectory сервера, получает ресурсы и запускает выбранный ресурс в плеере Lampa, если формат и сетевой доступ совместимы.

## Протоколы

- SSDP: UDP multicast на 239.255.255.250:1900 для поиска и объявлений UPnP.
- Device description: HTTP XML с описанием устройства и сервисов.
- ContentDirectory: SOAP Browse для навигации по каталогу.
- AVTransport: SOAP SetAVTransportURI, Play, Pause, Stop, Seek, GetPositionInfo и GetTransportInfo — при поддержке конкретным Renderer.

## Ограничения браузерного слоя

Стандартный WebView JavaScript не имеет универсального API для UDP multicast. WebSocket и Fetch не заменяют SSDP UDP. Поэтому возможны три пути:

1. Найти уже существующий документированный API в AndroidJS конкретной сборки Lampa.
2. Если такого API нет — реализовать ограниченный ручной режим с известными адресами и HTTP-доступом, если политика WebView позволяет.
3. Если автоматический SSDP обязателен, потребуется native bridge/APK или постоянно доступный локальный посредник. Это противоречит исходным ограничениям пользователя, поэтому такой путь не считать решением по умолчанию.

## CORS и локальная сеть

Даже если устройство отвечает по HTTP, WebView может блокировать чтение ответа из-за CORS, mixed content или сетевых ограничений приложения. Успешный ping/открытие IP в браузере не гарантирует доступность SOAP из JS.

## Форматы и дорожки

DLNA Renderer не гарантирует поддержку любого контейнера, кодека, профиля или URL. Переключение аудиодорожек и субтитров не является универсальной возможностью AVTransport. Эти функции зависят от Renderer, протокола передачи и самого медиапотока. В интерфейсе их следует показывать только при подтверждённой поддержке.

## Жизненный цикл запуска в Lampa 0.6.5

- В каждый момент разрешена не более чем одна pending-попытка `Lampa.Player.play()`. Следующая попытка допускается после завершения или принятого ручного/автоматического abandonment. Блокировка принадлежит запуску и переживает `Activity.pause()`/`destroy()`. Она не блокирует Browse: папки, список ресурсов, фокус, прокрутка, Back и повторное открытие каталога доступны. Попытка выбрать видео при блокировке показывает уведомление и не вызывает второй `Player.play()`. Back может закрыть каталог, но не подтверждает завершение плеера.
- Восстановление контроллера — отдельное право активного экземпляра DLNA-компонента. Новый экземпляр может принять право восстановления незавершённого запуска. При завершении он восстанавливает фокус и прокрутку только если всё ещё является текущей Activity и активен контроллер плеера. Settings и чужие Activity не переключаются.
- `Player.listener` события `external` и `close` подписаны один раз на срок жизни плагина через GUARD. Эти постоянные подписки не требуют `listener.remove`; подписки и обработчики отдельных компонентов, напротив, должны удаляться при `destroy`.
- Событие `external`, `blur`/`focus` и `visibilitychange` не подтверждают завершение. Завершение внутреннего плеера подтверждается callback Lampa или `close` с тем же объектом `data`.
- У `create.abort()` в доступном API нет callback/события подтверждения отмены. Без совпадающего external автоматическое разрешение после abort запрещено. Перезапуск приложения очищает JS-состояние, но физическую отмену Android-запроса не подтверждает. Таймаут и отсутствие события не считаются подтверждением.

### Разрешение следующей Android-попытки

Ручное recovery требует подтверждения пользователя. Автоматический путь требует текущую pending-попытку, совпадающий external и полный цикл hidden → visible после запроса запуска. Допускаются external → hidden → visible и hidden → external → visible. При visible до external цикл отклоняется.

Разрешение принимается однократно после возврата видимости, document.hasFocus() и навигационного управления исходной папке того же экземпляра каталога. Смена папки, Activity или экземпляра, Settings, чужое либо частично открытое окно, загрузка, ошибка и экран ресурсов инвалидируют незавершённый цикл. После временного перекрытия требуется новый полный цикл. Повторное открытие каталога и одиночный focus/start разрешения не дают.

Переход использует abandonment с отдельной причиной auto-return-unconfirmed. Он не вызывает Player.play(). Новый запуск требует свежего ввода. После принятого разрешения экран ресурсов допускает свежий OK или указатель. Остаточный keyup, удерживаемый OK и устаревший клик отклоняются.

Функциональные подписки отделены от диагностики. Наблюдения хранят числовые поколения и идентификатор попытки, без ссылок на уничтоженные компоненты и DOM. Журнал ограничен и исключает URL, credentials, названия видео и идентификаторы папок.

### Сохраняющиеся ограничения

- Публичный коррелированный сигнал, доказывающий завершение конкретного Android-запроса и невозможность его позднего запуска, в проверенных исходниках не найден.
- Возможен фактический порядок нативных запусков p2 → p1. Этот контрпример сохранён в тестах. Возврат через Home может разрешить следующий выбор при ещё работающем плеере.
- Синхронный сторонний подписчик Settings/open может открыть чужое окно или сменить Activity, после чего штатное продолжение Settings перехватит фокус. Штатный источник исследованных вмешательств в проверенной ревизии не найден.
- Сохраняется ранее установленное ограничение раннего вложенного recovery-Modal.
- Основа проверки Lampa — ревизия 6b5d9215db4015d3037915dcfbf1fcbee85f30c2. Соответствие установленному APK требует отдельной проверки.

## Критерий готовности

Функция считается реализованной только после теста на реальном Android TV устройстве и фиксации модели/прошивки, версии Lampa, поддерживаемого сервиса и результата. Наличие UI-кнопки или успешного XML-запроса не является доказательством полноценной поддержки DLNA.

### Ручное испытание 0.6.3

По сообщениям пользователя и фотографиям журнала подтверждены возврат из корня в DLNA Bridge, Back из вложенной папки, три цикла каталог → настройки → каталог, навигация в общих настройках, сохранение Android lock и отмена recovery через Back/«Отмена». Подтверждение recovery требует отдельного выбора видео. Двойной OK на подтверждении сам видео не запустил.

В журнале p6 зафиксированы recovery-cancelled, launch-blocked в external и позднее recovery-accepted/playback-abandoned с причиной user-permission-not-completion. Следующий pending p7 появился примерно через 6,4 секунды.

Устройство указано пользователем как Xiaomi Mi Box S 4K, Lampa Android 1.13.5-581, веб-версия 3.4.5, плеер Android. Версии перед тем прогоном повторно не сверялись. На устройстве не проверялись второй файл, Back во время загрузки и из ресурсов, искусственные поздние события и вмешательства сторонних подписчиков. Отсутствие скрытых вызовов и утечек памяти ручным прогоном не установлено.
